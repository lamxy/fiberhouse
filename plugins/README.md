## 设计意图

FiberHouse 的扩展目前由 Provider / Manager / Location 承担：Provider 是细粒度的扩展单元，按 `Type()` 区分职责、按 `Target()` 区分引擎实现。这套机制足够灵活，但代价是启动阶段的配置复杂度——接入一个完整场景往往要逐个注册十几个 Provider，且注册顺序与位点需要调用方自行掌握。

`plugins` 计划在 Provider 之上补一层**场景化打包**：把一组 Provider 及其注册顺序、初始化配置收敛成一个可插拔单元，让调用方在启动阶段选择一个 plugin，而不是手写整串注册代码。

分层关系：

- **Provider** —— 细粒度扩展单元，职责单一，是能力的实际载体。
- **Plugin** —— 把一组 Provider 打包成场景化预设，是启动期的装配入口。

Plugin 不取代 `Target()`，也不改变 Provider 的语义；它只负责"按场景一次性装配好该装的东西"。

## 术语边界

**这里的 "plugin" 指编译期组装、启动期装配，不是运行期动态加载。** Go 的 `plugin` 包在跨平台与版本一致性上限制过多，本目录不打算基于 `.so` 做热加载。plugin 以普通 Go 代码形式存在，随应用一同编译，只是在启动流程中被显式挂载。
